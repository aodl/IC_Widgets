# Membership review engine

The pure engine receives one or two full proposal captures, a completed Registry baseline, a scenario choice and a versioned policy. Inputs are immutable after validation. It reads no system canisters, clocks or storage. Each ordered scenario runs independently from the same baseline. An unsuccessful step has no after-state, and subsequent steps in that order are marked skipped. The successful prefix still retains every intermediate state and its findings.

## Registry semantics

The engine preserves the original instruction vectors and ordered memberships. Function 31 checks that every removal occurs in its target, prepends additions and filters removals from both lists. An overlap takes the removal path after validation. Function 2 validates requested API boundary assignments and prepends additions. The shared replacement helper applies adjacent `Vec::dedup`. The Registry still rejects a nonadjacent duplicate after that step, so the same already-member request can succeed or fail depending on membership order. Function 13 filters each listed subnet, emits mutations only for changed subnets and leaves unassigned or unknown removal candidates visible as no-ops. Function 18 is a separate unsupported action. [Released mutation sources](https://github.com/dfinity/ic/tree/00e4d8e3ee6081c1862e6119d63cffa76bd4af3d/rs/registry/canister/src/mutations)

For affected listed subnets, the engine checks registered membership, uniqueness, nonempty membership, exclusive replica/API boundary assignment, Cloud Engine reward type and SEV chip identity. It assumes invariants independent of membership already hold in the published baseline. Results model Registry membership mutations under the pinned rules. Other execution failures and later Registry versions can change eventual Governance outcomes. A requested unlisted subnet record is explicitly unsupported. A conflicting or undecodable listed topology prevents baseline resolution. [Released subnet invariants](https://github.com/dfinity/ic/blob/00e4d8e3ee6081c1862e6119d63cffa76bd4af3d/rs/registry/canister/src/invariants/subnet.rs) · [Assignment invariant](https://github.com/dfinity/ic/blob/00e4d8e3ee6081c1862e6119d63cffa76bd4af3d/rs/registry/canister/src/invariants/assignment.rs)

Open and adopted captures support hypothetical execution. Rejected and failed captures yield a typed terminal result. Executed captures require evidence of an earlier Registry head; even then the result is a hypothetical run against that earlier baseline. An exact historical before-state requires separately establishing the execution's Registry mutation version. Source clocks and read times alone cannot establish it.

## Evidence and revision

The builder requires evidence for the roster, all listed subnet records for assignment, and any explicitly selected target. It joins only the nodes relevant to the candidate actions and affected subnets, plus the operator, data-center and boundary rows needed for those nodes. Omitted joins are errors. Missing, deleted and unavailable records remain explicit. Missing keys are findings of a completed sparse projection at the specified version, without an independent cryptographic absence proof.

The manifest binds record mutation versions, source times, page/chunk observation IDs and retained value hashes, plus full proposal capture observations, status, raw and payload hashes, the ordered selection, analysis and policy versions, and an optional metrics revision. The digest uses Candid over typed structures with sorted map iteration, and includes a digest of the resolved Registry and decoded proposals. The revision is the SHA-256 of the schema-tagged manifest. The source producer validates the capture and provides the archived bytes. Registry replay stores selected complete values separately; the full source page is identifiable by hash and its unselected wire fields cannot be reconstructed. See [evidence storage](EVIDENCE.md).

## Analysis rules

A state retains membership order, added/removed/retained sets relative to the baseline, counts, net change and coverage. Provider and operator groups use principals. A data-center ID comes from the lower-cased Registry key. Owner values are trimmed registered labels. These groups do not establish physical location or beneficial ownership.

Registered geography uses the first two fields of a comma-delimited continent/country declaration. Recognized continents use two-letter codes and English names. Country codes normalize regular CLDR 48 territory mappings with assigned alpha spellings, excluding the private-use XK code. UK is normalized to GB. Unrecognized parts remain unknown independently. The original region remains in the Registry record. The table comes from the supplemental territory mapping and validity data under the Unicode license. [CLDR code mapping](https://github.com/unicode-org/cldr/blob/release-48/common/supplemental/supplementalData.xml) · [CLDR validity data](https://github.com/unicode-org/cldr/blob/release-48/common/validity/region.xml)

Distributions count known groups and unknown members on every dimension. Minimum and maximum use known groups, and mean carries its exact numerator and denominator. For conventional replica subnets the strict one-third threshold is `floor(n / 3) + 1`. The fault-budget threshold is `floor((n - 1) / 3) + 1`. Groups are accumulated largest first, and the coefficient requires complete dimension coverage. Policy v1 warns if the selected coefficient decreases or the largest group's share increases with complete coverage. It compares shares by integer cross-multiplication.

Distances use registered GPS rounded to 1e-7 degrees, checked for legal latitude and longitude. Great-circle distance uses the haversine formula and the legacy 6,376,500-metre radius. Each unordered node pair contributes once, weighted through identical coordinate groups. Pair distances are rounded to the nearest metre, followed by the rounded mean. The view reports valid and total pairs and no distance statistic when fewer than two nodes have valid coordinates.

## Scope and blockmaking

The resolved scope carries the review and evidence revision, ordered proposal IDs, scenario, baseline version and target subnet. Its nodes are the union of baseline members and every candidate in that scenario, including rejected/redundant candidates. It retains requested roles and participation before and after each step. Final roles are present only in complete scenarios. Filters intersect the inherited node set, including empty sets. Unavailable scope propagates, and implicit intersection requires identical scope identity. Explicit comparison keeps each side intact.

The pure blockmaking contract rejects a node or subnet outside the resolved scope. It separates counter rows, sparse omissions, missing samples, conflicts, reappearance and subnet transitions. Only two observed rows in an established epoch may yield counter deltas. Decreases indicate resets. An observed zero denominator has a separate result. These are consensus blockmaking observations.
